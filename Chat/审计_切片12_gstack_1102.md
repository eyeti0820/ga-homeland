## 三、并发与API

### P2-1 meet_state KV四写者无串行, last-write-wins可丢seamless清位[低概率, 建议择机加锁]

写者: ①mode_post两分支(读在事件循环、写在to_thread) ②post_msg清位(全同步) ③`_state_line`noted翻位(读同步、写to_thread)。同步段在单事件循环内原子, 但**to_thread写落盘可被其他协程插队**。最现实的交错链:

> 纠偏切chat(seamless=1) → 用户连发消息A → A的生成轮启动, `_state_line`读到{seamless:1,noted:False}, 翻noted后await线程写 → 生成期间用户发消息B → post_msg同步清seamless=0落库 → A轮的线程写后落: **{seamless:1,noted:True}整dict覆盖, 清位丢失** → 此后B/C/D全是真隔屏消息, 但下回进面仍被误判同段, 且首条见面消息会补出第二个"开始"(与既有"结束"横幅矛盾)。

窗口毫秒~秒级, 需"退出后首条消息的生成期内追发第二条", 概率低但聊天产品里连发常见。同类既有风险: closeMeet的exit POST在途时秒速重进, exit写后落会把meet态整dict覆盖回chat(见面屏挂着KV却是chat, 前置存在, 非本次引入)。**修法**: per-char `asyncio.Lock`串行四写者, 或meta表改为字段级UPDATE。不修也自愈(下次真发消息/显式退出即纠正)。

### P2-2 非quiet chat切换也写seamless=1, 与自身横幅矛盾[API-only]

设计文案"其余**quiet**切换→seamless=1", 代码(chatapp.py:1409)不看quiet。直连API发非quiet chat切换: 落"结束"横幅行却置seamless=1→重进同段(since不变)→首条见面消息因last_evt=chat再补"开始"→**同一段内出现"结束+开始"横幅对而状态行宣称连续**。前端三处chat调用全带quiet:1, 不可达; 建议代码对齐文案(`seamless: 0 if exit_meet else (1 if quiet else 0)`)或改文案。

### P3-3 exit在meet分支被静默忽略; 值不校验

mode=meet带exit:1→exit只在chat分支读取, 静默忽略(无害)。exit任意truthy(JSON串/数字)bool coercé均当真——无注入面(JSON整dict落KV仅此三键), 无害。

### P3-4 openMeet的mode失败静默吞(前置存在, 与1101修法不一致)

index.html:952 `catch(e){}`空吞: mode POST失败则见面屏挂着而KV仍chat+seamless(或1)→见面消息被chat打标+误补"结束"。pickScene同类问题1101已改toast(index.html:1046), openMeet未跟进。建议补同款toast。

## 四、技术债

### P1-1 post_msg清位是事件循环上的同步阻塞写+双重读[应修, 同类问题二次回归]

- chatapp.py:1638 `_meta_set(...)`直接在async handler里同步写SQLite——而1394/1412行同类写均包了`asyncio.to_thread`且注释明写"审计P2-2: 阻塞写挪出事件循环"。**P2-2已修过一次的同款模式回归**, SQLite忙等(与worker线程写并发)时会卡住整个事件循环(含poll轮询)。
- 附带: 1632行`_mode_of(char)`已读过一次KV, 1635行`_get_meet_state(char)`再读一次——每条chat消息多一次DB往返。修法: `st_ = _get_meet_state(char)`单读, `cur_mode = st_.get("mode")`, 写包`await asyncio.to_thread(_meta_set, ...)`(注意包await后与下文`_lazy_banner`的await顺序无依赖, 安全)。
